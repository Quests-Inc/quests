## Предлагаемые правила

Два макета: список/дерево слева и рабочая область справа; либо верхняя панель и содержимое ниже. Календарь — исключение. Вложения могут сохранять внутренний просмотр рядом со списком: это содержимое второго макета.

Шаблоны и раннеры переводим во второй макет. Шаблоны сохраняют список → экран редактирования → назад. Раннеры сохраняют обзор устройств и заданий, получают общую панель устройства/состояния; дополнительный сайдбар пока не нужен.

Заголовки используют обычный цвет текста и общий существующий типографический токен; декоративные значки убираем. Акцент обозначает действие или выбор. Ширину страницы не ограничиваем произвольными 72/76rem; ограничение читаемости допускается внутри формы, а не для всей вкладки.

Поиск растёт по свободному месту. Сегменты имеют естественную ширину. При нехватке места группы переносятся целиком, подписи статусов не разрываются. На телефоне длинные наборы доступны через существующий picker. Панель фиксирована в пределах страницы, содержимое имеет один основной скролл; вложенные скроллы оставляем для редакторов/логов/таблиц по необходимости.

В запусках: первая строка — состояние; ниже — тип источника; затем компактные снимаемые метки конкретного источника/скрипта и общий сброс. Фильтр типа и конкретный источник должны согласованно менять друг друга, URL и пустое состояние. Не добавляем фиктивный поиск без поддержки данных API.

## Компоненты и Svelte

Переиспользуем `SidebarLayout`, `SidebarTools`, `SidebarPicked` (массовый выбор), `OptionPills` (короткий набор вариантов), `Picker` (выбор), `FilterSelect` (множественный фильтр), `DateInput`, `RunnerPicker`, `Toggle`, `FlagHints`, `FormSection`, общие кнопки и токены.

Добавляем минимальные компоненты: оболочка верхнего макета с toolbar/content snippets; общая панель с поиском/действиями/фильтрами; заголовок страницы; снимаемая метка фильтра; общие состояния загрузки/пустоты/ошибки, если инвентаризация подтверждает одинаковую семантику. При необходимости расширяем OptionPills счётчиком и слотом значка, не создаём второй набор сегментов.

Страницы отвечают за запросы, маршрутизацию, специфичные действия и содержимое. Общие компоненты отвечают за разметку, адаптивность, доступность и визуальное поведение. Не создаём компонент с флагом на каждую страницу. Повторяющийся код запроса выносим лишь при совпадении жизненного цикла; абстракция сетевого состояния не обязательна для унификации CSS.

После миграции удаляем дубли `hookpage__seg`, `attpage__seg`, `hist__seg`, `runs .seg`, их стили и адаптивные ветки. Страничные формы постепенно освобождаем от классов `modal__*`, сохраняя общие form-примитивы.

Последовательность: проверить общий макет на хуках и шаблонах; затем вложения/история/раннеры; затем фильтры запусков и оставшиеся дубли. Проверить длинные названия, узкий контейнер и телефон, клавиатуру, темы, загрузку/ошибку/пустоту. Обновить docs/ui-style.md и note=332, note=333, примеры note=390 после согласования.

## Мигание запусков

`RunsPage.svelte`: `refreshOpen()` раз в 1500 ms вызывает `open()`, который делает `detail = null`. UI каждый раз заменяет данные на «Загрузка запуска…». Первичная загрузка и фоновое обновление должны быть разными операциями. При обновлении сохранять данные, раскрытие и скролл; принимать ответ только для актуального выбранного запуска, отменять устаревший запрос/таймер, ошибку обновления показывать рядом с данными. Опрос только пока вкладка активна и запуск ожидает; после сетевой ошибки возможен повтор с задержкой.

## Прод: «Почта», чтение 2026-11-10

Запуск 144: template=5, script=13, graph_ref `script:13:2`, создан и последний раз изменён 2026-10-19 16:30 UTC. Нода 2 `code` — waiting; `jobs` пуст. Очередь заданий пуста. arch-home и main-pc онлайн, laptop-n95 офлайн. Текущий template=5 использует `arch-home,main-pc`.

Последние выпуски 8, 9, 10 ноября имеют статус ok, 0 items, сообщение `miss: the command printed no quest`; сегодняшний занял 2015 ms. Это штатный пустой результат скрипта, а не доказательство отсутствия писем в ящике. Скрипт повторно не запускался, секреты и содержимое писем не читались.

Доказано рассогласование исторического запуска и очереди, а не текущая недоступность раннеров. Точная причина пока не доказана: `PurgeRunnerJobs` удаляет завершённые задания старше 14 дней; `PurgeRuns` никогда не удаляет waiting. Старое завершённое задание могло быть очищено, но это гипотеза. Нужны исторические логи/БД для установления первичного события. Исправление должно предусмотреть сверку waiting с заданиями и явное состояние потерянного результата, а также безопасную политику хранения. Не следует автоматически повторять код: он может иметь побочные эффекты.
